# Milestone 3: offline evidence retrieval and investigation

## Existing implementation review

Reviewed ingestion.py, triage.py, state.py, service.py, cli.py, both existing migrations, all existing fixtures/tests and milestone-2.md. Ingestion hashes canonical [index, document ID] into the foundation source identity; the processing UUID is what --alert-id selects. Original JSON and SHA256, normalized ancestors (including type/depth), policy decisions and entity context are immutable. Ancestors are references, not sequence contents. Dotted/nested ECS access rejects conflicting representations. The existing parser supplies bounded JSON validation. Lifecycle triggers and audits remain intact; investigating is entered when a first report is saved. Partial evidence does not mark the alert completed or failed. Existing completed/failed alerts can be examined without rewriting their lifecycle.

The repository's existing abstractions were extended, not replaced. No network, Elastic Cases, response, model, additional detector, correlation engine, or external platform is involved. All new fixture contents are synthetic.

## Provider contract and fixture format

EvidenceProvider exposes retrieve(Reference) and retrieve_many(list[Reference]), returning Retrieval objects with found, missing or failed status. Every result must match the requested index/ID. Found hits must also contain matching _index and _id and an object _source. The engine independently validates even alternative providers. Failures cannot supply a document. Missing files and retrieval/JSON/identity failures are distinct. No alert document is substituted for a missing source event, and ancestor references are not traversed recursively.

FixtureEvidenceProvider reads exactly one exported hit per file. Filename is SHA256(canonical JSON [index,id]) + .json, generated by its filename method. Input references never become paths. Symlinks are rejected. Reference characters are conservatively restricted to ASCII letters/digits and _ . : @ + -, maximum 512 characters; dot/dot-dot, URLs, wildcards, slashes, control characters and missing identities fail. Future Elastic indices/IDs outside this subset require a reviewed relaxation.

Each file is read with a 256 KiB + 1 bound; existing parser rejects duplicate keys, nonfinite values, excessive nesting, oversized JSON and batches. Validated serialized provider hits also have a 256 KiB bound. Requests allow at most 100 selected alerts and 100 ancestor occurrences, including duplicates. Thus total retrieved input is bounded to 25 MiB before canonical JSON overhead. Duplicate references are retrieved once; every supplied ancestor occurrence, including type/depth and extra metadata, remains in the report.

## Investigation semantics

service.investigate loads immutable ingested alerts for explicitly selected processing UUIDs. There is no automatic alert grouping. request_identity sorts and deduplicates alert IDs. Each exact source reference is resolved once and validated. @timestamp is parsed with a required timezone and normalized to UTC for chronological ordering, with index/ID as deterministic tie breakers. Missing/malformed timestamps remain evidence and facts where context is valid, but are omitted from the timeline and reported as gaps. No alert timestamp substitutes for an event timestamp.

Observed facts contain source context and exact evidence references. Associations use exact nonempty process.entity_id, process.parent.entity_id, user.id, session.id and host.id matches, plus process entity to parent entity references. They carry association_only certainty and causation_established=false. Host names, rule identity, severity, chronology and proximity never establish an association. Shared host/user/parent identifiers can be weak associations; the report exposes supporting fields rather than asserting a causal chain, successful escalation or compromise. Event actions are preserved descriptions, not interpreted detection rules. Unknown compromise and causal relationships remain explicit questions.

Report schema_version=1 includes deterministic investigation ID, request fingerprint, selected alert IDs, full references, retrieval statuses and original hits/hashes, timeline, observed facts, supported inferences, gaps, status, generation time, engine_version=3.0 and audit correlation UUID. completed means evidence processing completed, not confirmed compromise; partial means evidence is unavailable or unusable. Reports and source hits may contain sensitive evidence: protect the database and CLI JSON outputs with existing deployment permissions and umask guidance. Logging never includes evidence.

## Persistence and repeat execution

Run init-db to migrate. Additive migration 003 retains migrations 001/002 and adds investigations, investigation_alerts, investigation_references, investigation_evidence and investigation_audit. Foreign keys bind requests to alerts. Every new table has update/delete prevention triggers. The global evidence table pins each retrieved (index, ID) to its canonical document hash and original hit. All report, reference, source evidence, lifecycle and success audit writes use one BEGIN IMMEDIATE transaction. An exception rolls all of them back, then a separate transaction appends a failure audit with a correlation UUID and no submitted contents. If storage itself cannot accept audit writes, durable failure audit cannot be guaranteed.

Investigation ID is inv- plus SHA256(canonical [engine version, sorted unique processing alert UUIDs]). The same request re-retrieves evidence and compares a fingerprint of the entire canonical retrieval snapshot, including missing/failed statuses. Equivalent selection and evidence return the exact original report and append a duplicate audit with the new attempt correlation UUID. Changed evidence/status under that request is rejected; found evidence conflicting with any previously saved source identity is also rejected across requests. Prior results are never replaced. Failed attempts create no success report and can be retried safely. Failure audit is deliberately separate from report status.

Future explicit re-investigation needs a revision/request-generation key and links to prior reports; evidence revisions need versioned snapshots rather than overwriting pinned source identities. Neither workflow is implicitly enabled by changing fixtures. Engine upgrades create different request identities but still respect pinned evidence.

## Offline usage

```sh
soc-automation init-db
soc-automation ingest --file tests/fixtures/investigation/stages.json
soc-automation investigate --alert-id FIRST_UUID --alert-id SECOND_UUID --alert-id THIRD_UUID --evidence-dir tests/fixtures/investigation/evidence
soc-automation show-investigation --investigation-id inv-FINGERPRINT
```

Use the existing SOC_DATABASE_PATH and configuration conventions. Both new commands print structured JSON. Existing show-alert/triage accept one alert ID; investigation allows repeated --alert-id. Errors retain existing exit/log conventions.

## Fixtures and validation

stages.json contains three distinct alerts, each referencing only its own separate authentication, execution or privilege-change event. Events share selected user/process identifiers; event ordering and association remain separate. partial.json adds duplicate references, two unusable timestamps, missing evidence, incorrect returned identity and an event lacking linking identifiers. conflict.json provides changed content under a pinned identity. Hashed fixture files contain the actual source events.

New tests cover retrieval, missing/failed identities, bounded and malformed JSON, symlinks, malformed references, resource limits, partial/ordered timelines, unsupported causal claims, explicit multi-alert selection, duplicate references, repeat/restart persistence, conflicts across requests, audit records, transactional rollback and JSON CLI integration. Existing network-blocking autouse fixture applies to the complete suite.

Validation: `/tmp/soc-foundation-venv/bin/python -m pytest -q` (99 passed); `python -m ruff check .` and `python -m ruff format --check .` using the same environment. No network was accessed by tests.

## Limitations and next integration boundary

This milestone is offline only. No recursive alert ancestry expansion, causal reconstruction, semantic event classification, enrichment or incident confirmation occurs. The fixture filesystem and SQLite are trusted local storage, not tamper-proof boundaries. Readers reserve SQLite's writer lock as before. Successful reports retain full source hits; output size is bounded by input limits but can be sizable. No automatic retries, evidence revisions or reinvestigation workflow exists.

The exact-identity provider boundary is ready for a future read-only Elasticsearch adapter. That work must separately address permissions, deployed schema/index semantics, transport errors, batching, timeouts and response limits; it is not implemented here. Milestone 3 does not change Elastic Security's ownership of detection/EQL or Elastic Cases' ownership of cases.
